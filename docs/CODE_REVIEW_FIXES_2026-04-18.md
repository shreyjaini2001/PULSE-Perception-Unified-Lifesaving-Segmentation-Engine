# Code Review Fixes - 2026-04-18

This note records the three highest-priority issues found during the repository review and the changes applied to address them.

## Scope

The fixes in this pass target:

1. Scan-mode face capture silently dropping face embeddings and thumbnails.
2. SALT/MARCH under-triaging a treated but still life-threatening hemorrhage case.
3. Dashboard profile changes failing to reload the full model stack.

## Changes Applied

### 1. Scan face embedding path fixed

File:

- `edge-node/pipeline/scan_engine.py`

Problem:

- `FaceReID.embed_person()` returns three values: embedding, face crop, and face bounding box.
- `ScanEngine.capture()` unpacked only two values.
- The resulting exception was caught and logged, which made the scan appear to succeed while silently dropping the face embedding and face thumbnail.

Fix:

- Updated the scan path to unpack all three return values and ignore the extra face bounding box when it is not needed.

Expected impact:

- Scan captures now preserve face embeddings.
- Face thumbnails now populate again when a face is available in the sweep frames.
- Re-identification quality for scanned casualties improves because the embedding is no longer discarded.

### 2. SALT now treats tourniquet-managed hemorrhage as RED-worthy until confirmed

Files:

- `edge-node/state/salt.py`
- `scripts/smoke_test.py`

Problem:

- `derive_march()` marks a detected or stated tourniquet as `Status.TREATED`.
- `suggest_salt()` previously escalated to `RED` only when hemorrhage was still `CRITICAL`.
- That allowed an obvious high-risk case such as a gunshot wound with a tourniquet and tachycardia to fall through to `YELLOW`.

Fix:

- Added `Status.TREATED` massive hemorrhage to the SALT RED-driving conditions.
- Excluded treated massive hemorrhage from the GREEN fast path.
- Updated the smoke test to assert that the existing tourniquet scenario now returns `RED`.

Expected impact:

- A casualty with severe bleeding that has been managed with a tourniquet remains prioritized as an immediate casualty until a medic confirms otherwise.
- The smoke test now guards against this regression.

### 3. Profile changes now reload the full pipeline bundle

File:

- `edge-node/main.py`

Problem:

- Profile changes from the dashboard previously replaced only the wound backend.
- The rest of the active stack continued using the old profile selection, including person detection, audio, face re-ID, rPPG, LLM, anomaly prior, and scan engine wiring.

Fix:

- Added a full stage-bundle builder and installer for the live pipeline.
- Profile reloads now rebuild and atomically swap the complete active bundle under a pipeline lock.
- Existing face embeddings are re-seeded into the new face re-ID stage.
- Cache state tied to the old stages is cleared during the swap.
- Removed the obsolete wound-only reload helper.

Expected impact:

- The selected dashboard profile now affects the full live stack rather than only the wound model.
- Subsequent scans and live processing use the newly selected model tier consistently.

## Remaining Known Risks

These were identified during review but were not changed in this pass:

- The transcript/audio state is still scene-global and then copied onto each visible casualty.
- The receiver dashboard still depends on remote assets for some UI and 3D functionality, so it is not fully offline-first.
- The shipped `balanced` profile still appears heavier than the README guidance for 8 GB VRAM systems.

## Prototype Refinement Pass

An additional refinement pass was applied after live testing with the webcam and dashboard.

### Identity and workflow improvements

Files:

- `edge-node/main.py`
- `edge-node/pipeline/face_reid.py`
- `edge-node/pipeline/person.py`
- `dashboard/app.js`

Changes:

- Autogenerated victim labels were changed from phonetic call signs such as `Alpha-1` and `Bravo-2` to neutral operator-facing record IDs such as `CAS-001`.
- Added a recent-bounding-box fallback in the edge node so tracker churn is less likely to create a duplicate provisional victim record before face re-identification stabilizes.
- Suppressed the known protobuf deprecation warning emitted by a dependency so operator logs stay cleaner during runs.
- Updated the casualty list so scanned casualties sort ahead of provisional live detections.
- Updated the tile language so unscanned detections read as provisional/live and scanned casualties read as stored records/rescans.

Expected impact:

- Fewer duplicate casualty cards for the same person during live use.
- Cleaner terminology for medics and judges.
- A casualty list that better matches the intended workflow: lead medic scans first, follow-on medics act from the frozen priority records.

## Wound Debug Follow-Up

An additional wound-detection follow-up was applied after inspecting saved debug artifacts from a missed obvious arm injury shown on a monitor during live testing.

Files:

- `edge-node/pipeline/wound.py`
- `edge-node/config/scenarios.json`

Changes:

- Added relabeling for low-confidence `amputation` / `tourniquet` style detections that visually look like broad surface trauma, converting them into `abrasion` or `burn` before the final evidence gate.
- Added an explicit `abrasion` evidence branch so diffuse textured skin trauma is not treated like a generic wound.
- Slightly loosened the high-risk acceptance path for `amputation` / `tourniquet` labels when structure and retained area are strong.
- Replaced the `amputation stump` blast prompt with `mangled extremity wound` to reduce prompt bias toward literal amputation labels in the hackathon demo profile.
- Added zero-proposal recovery in the wound segmenter: a prompt-sweep fallback plus a surface-trauma heuristic for broad burn / abrasion regions when GDINO returns no candidates on a monitor-captured or blurry demo frame.

Expected impact:

- Obvious abrasion / road-rash style injuries are less likely to be rejected after successful proposal generation and segmentation.
- The demo stack is less likely to mislabel broad traumatic skin damage as `amputation`, then filter it out on confidence.
- If GDINO emits no wound boxes at all, the scan can still surface a body-gated burn / abrasion region instead of silently returning `0 wounds`.
